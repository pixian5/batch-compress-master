# 解压解析实现说明

更新时间：2026-08-08

维护者模型：GPT-5

## 适用范围

本文是 `/Users/x/code/Google-compress/解压.md` 中历史方案的实施覆盖说明。当前创建格式严格限制为 `rar`、`7z`、`zip`：RAR 使用官方 RAR，7z/ZIP 使用官方 7zz。解压时可以识别 7zz 支持的其他常见格式，但目录扫描和命令行格式选项仍以项目已验证的格式为准。

当前识别的分卷命名只有三类：

| 类型 | 命名 | 引擎 |
| --- | --- | --- |
| RAR 分卷 | `name.part01.rar`、`name.part1.rar` | RAR |
| 7z 数字分卷 | `name.7z.001` | 7zz |
| ZIP 数字分卷 | `name.zip.001` | 7zz |

旧式 RAR `.r00` 和传统 ZIP `.z01` 不属于当前程序支持范围，不能按本规则猜测。

## 统一解析器

`Core/Services/ArchiveVolumeResolver.cs` 的 `Resolve` 是唯一分卷解析入口。它一次返回：

- 实际归档类型和后缀；
- 实际首卷路径；
- 按数字排序的整组卷；
- 缺失编号；
- 同编号冲突；
- 大小写不敏感查找歧义；
- 是否存在首卷及是否允许解压。

调用方不得重新构造 `part`、`.7z.NNN` 或 `.zip.NNN` 正则。压缩成功后的移动/删除也必须使用同一解析结果中的 `FilesForPostProcessing`。

## 路由优先级

解压路由遵循以下顺序：

1. 实际文件名明确为 RAR，使用 RAR。
2. 实际文件名明确为 7z、ZIP 或 7zz 支持的其他格式，使用 7zz。
3. 文件名没有可识别格式时，使用 `ArchiveOptions.ArchiveFormat` 作为兜底。
4. 压缩创建格式不允许未知值；未知创建格式直接返回 `NotSupportedException`，不能把 `.tar` 等未知格式伪装成 RAR。

因此 `a.7z + ArchiveFormat=rar` 仍使用 7zz；矛盾的 `ArchiveFormat` 不能覆盖实际文件类型。无后缀文件才允许通过选项明确指定 RAR。

## 分卷完整性

“编号连续”和“归档可解压”是两个不同概念：

```text
可解压 = 存在编号 1
      && 编号没有重复
      && 1 到最大编号之间没有缺号
      && 没有大小写歧义
```

例如 `002、003` 数字上连续，但因为缺少 `001`，必须跳过，不得把 `002` 当作首卷交给引擎。`001、003` 则报告缺少 `002`。末尾是否还存在一个程序无法从文件名推断的卷，最终仍由官方归档工具返回码和错误输出判断。

大小写后备查找规则是：精确路径优先；精确路径不存在时进行不区分大小写搜索；零个结果是未找到，一个结果可使用，多个结果必须判为歧义并跳过。

## 统计契约

`RequestedCount` 是密码本或压缩清单中的请求行数，读取有效行后立即递增。其余状态分别统计：

- `MatchedCount`：当前结果模型中由 `Entries.Count` 或 `Paths.Count` 表示；
- `NonExistCount`：没有任何实际文件；
- `IncompleteVolumeCount`：缺首卷或中间缺卷；
- `AmbiguousArchiveCount`：大小写歧义或编号冲突；
- `FailCount`：引擎启动后返回失败；
- `PostProcessFailCount`：压缩/解压成功，但移动或删除失败；
- `IgnoreCount`：重复任务、已处理项目或前置校验跳过。

命令行遇到引擎失败、后处理失败、分卷不完整或归档歧义时返回非零退出码，便于脚本可靠判断结果。

## 后处理安全性

移动前先检查整组目标是否存在。只要任意一个目标冲突，整组源卷全部保留，不删除、不覆盖、不形成半组移动。单个移动异常会增加 `PostProcessFailCount`，即使归档引擎本身已经成功，也不能在最终摘要中伪装成完全成功。
