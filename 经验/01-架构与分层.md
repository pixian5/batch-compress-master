# 架构与分层经验

> 基准 `0.7.6`。结论以当前源码为准；末尾「历史来源」仅作追溯。

## 1. 入口判定要「早」，能不初始化框架就不初始化

`--help`、`--version`、参数错误都在初始化 Avalonia（图形界面框架，Avalonia）之前返回。
好处是命令行用户不会凭空拉起一个图形界面进程，也不会产生日志或归档引擎对象；
参数错误必须返回非零退出码，绝不能带着残缺的默认选项继续跑任务。
**当前核实**：`Program.cs` 的判定顺序即如此；`--version` 实测输出 `0.7.6`。

## 2. 图形界面与命令行必须共用同一套业务内核

两套入口各自 `new ArchiveEngineRouter()` 并注入 `BatchOperationService`，
所以两端支持的格式、密码、分卷、后处理完全一致。曾出现过的「命令行能做、界面不能做」
这类漂移，根源就是各写一套收集/执行逻辑。
**当前核实**：`HeadlessBatchRunner` 构造、`MainWindowViewModel.CompressAsync` 均调用同一个服务。

## 3. 界面层不拼 Shell 命令

视图模型只做「收集输入 → 快照选项 → 调用服务 → 接进度」；参数生成下沉到命令构建层，
进程启动下沉到唯一的 `ArchiveProcessRunner`。这样路径空格、引号转义、注入风险只在一处处理。
**当前核实**：`MainWindowViewModel` 内无 `ProcessStartInfo`。

## 4. 用「表征测试」锁住行为，再做重构

批次 0-6 重构的做法是：先把消息文本、七类计数、关机时机、文件系统副作用写成断言锁死，
再抽公共骨架；重构后 `BatchOperationService` 从 1020 行降到 425 行、
`MainWindowViewModel` 从 1673 行降到约 1491 行，而 17 项表征测试零漂移。
**教训**：先有护栏再动刀，不要边拆边靠肉眼比对。

## 5. 条目级差异交给适配器，别在主管线里写分支

压缩与解压的预检、输出路径、分卷求和、失败回滚、消息文案差别很大，
由 `CompressionItemAdapter` / `DecompressionItemAdapter` 实现 `IBatchItemAdapter<T>`；
`BatchExecutionPipeline<T>` 只管循环、取消、计数、并发和关机。
主管线里堆 `if (isCompress)` 会让两条路径互相污染。

## 6. 归档成功与后处理成功要分开计数

「压缩成功但移动源文件失败」不能显示成完全成功，否则用户会以为文件已经清理。
后处理统一走 `PostProcessService`，失败逐条告警并并入该项结果消息。
**当前核实**：`BatchExecutionPipeline` 的串行路径与并发路径均如此统计。

## 7. 测试工程链接生产源码，而不是复制一份

测试 csproj 用 `<Compile Include="..\Core\**" Link="...">` 直接编译交付的代码，
保证测的就是实际发布的那份；新增服务类时要记得在这个 csproj 里登记，否则测试根本没编译它。
**当前核实**：`BatchCompress.Avalonia.Tests.csproj` 关闭了默认编译项，靠显式 `Compile Include`。
