# 版本与文档规范经验

## 1. 版本号只有一个来源

根目录 `VERSION` → csproj 用 `ReadAllText` 读它写进程序集版本 →
CLI `--version` 读程序集 → macOS 打包脚本写进 `Info.plist` 并回读校验。
禁止在别处手写版本号。每轮**修改源代码**后版本号加 `0.0.1`；新项目从 `0.0.0` 开始。
只改文档、依赖或配置不算修改源代码，不要顺手抬版本。

## 2. 两套文档目录职责不同

| 目录 | 放什么 |
| --- | --- |
| `文档/` | 长期文档：架构、命令行参考、快速参考、测试方案、UI 说明，以及历史设计稿 |
| `docs/` | 按时间排列的进度、决策、风险与实测报告 |

`docs/` 的文件名格式固定为 `YYYYMMDD-HHMM-标题-模型名.md`，
模型名写撰写那一刻实际在用的模型，不写死某个值，也不省略。

## 3. 写新 docs 必须同步登记索引

根目录 `文档索引.md` 介绍 `docs/` 里每份文档，README 指向它。
新增文档不在索引里加一条，等于没写。索引按时间倒序，表格一行一份。

## 4. README 要有【当前开发进度】【下一步待实现】

两节只写简短说明，并指向 `docs/` 里对应的「当前开发进度」「下一步待实现」详细文件。
README 的「文档」小节只登记**当前有效**的链接，不要把几十份历史快照全列上去——
过期的链接会误导后来者（本轮就修掉了指向 2026-09-30 的旧链接）。

## 5. `docs/` 的历史文档不一定对，必须复核

常见陷阱：

- 同一个主题有十几份「当前开发进度」「下一步待实现」，**只有时间最新的一份有效**。
- 同一份文件内部可能前后矛盾：许可风险说明前半段写「保留裸二进制」，文末「决策更新」已改为完整分发包。
- 早期报告里的版本号、测试项数、macOS 版本、代码行数是当时快照，不是当前状态。
- 曾经流传「项目没有持续集成配置」，实际已有 `.github/workflows/release.yml`。

**做法**：改代码前以源码 + 实测为准；历史文档只用来理解「为什么这么设计」。
本经验库每条都标注「当前核实」就是为了这个。

## 6. 注释说明动机，并带前缀

项目既有风格是在关键改动处写 `模型名, YYYY-MM-DD: 为什么这样改`。
重点记录「为什么」，而不是复述代码做了什么；尤其要写清被绕开的坑与取舍
（例如「日志不过滤密码」是用户明确选择的诊断行为，不能当成缺陷去「修」）。

## 7. 提交与推送

每轮改动完成后用中文写详细提交信息并推送，不必反复询问是否提交。
提交前把构建产物、临时文件等不必要文件加进 `.gitignore`；
本仓库已忽略 `bin/`、`obj/`、`.artifacts/`、`logs/`、夹具输出目录等。
`docs/` 与 `经验/` 的文档属于应提交内容，不要一起忽略。

---

**本目录自身的维护约定**：新增经验改写对应分类文件，不按时间堆新文件；
发现与源码冲突的表述立即修正，并在 [README.md](README.md) 的「已确认被推翻」表里补一行。
