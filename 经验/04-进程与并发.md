# 进程边界与并发经验

> 所有外部归档程序只经过 `ArchiveProcessRunner` 这一道门；并发问题几乎都出在「共享状态」上。

## 1. 参数逐项放进 `ArgumentList`，绝不拼 Shell 字符串

`ProcessStartInfo.ArgumentList.Add(...)` 逐项传参，天然处理路径里的空格与引号，也避免注入。
用于日志的「完整命令行」只是展示用，是另外拼出来的字符串，不参与实际启动。
`UseShellExecute=false`、`CreateNoWindow=true`、重定向 stdout/stderr。

## 2. stdout 与 stderr 必须并行异步读取

两个 `ReadToEndAsync()` 同时挂上再等进程退出；若先等退出再读，管道缓冲区写满会死锁。
日志保留原始输出（含明文密码），这是明确的诊断取舍，不要自作主张加脱敏。

## 3. 取消要杀整棵进程树

`Kill(entireProcessTree: true)` 后还要等待退出，并把两个读取任务收干净再抛出取消异常。
只杀父进程会留下正在写归档的子进程，产生半途废档。

## 4. 并发里的共享状态用一把锁，上报用克隆快照

`progressInfo` 的读写、成功/失败计数、累计大小、进度上报全部在同一把锁内，
上报前克隆一份快照，避免消费者读到「计一半」的撕裂状态。
默认并发度为 1，串行路径原样保留，保证升级后旧行为零漂移。

## 5. 「大小上限」和「取消」要用两个不同的令牌

| 场景 | 令牌 | 行为 |
| --- | --- | --- |
| 达到总大小上限 | 闸门令牌 | 只让**还没启动**的任务放弃排队，在途引擎自然完成，不产生废档 |
| 用户按 Ctrl+C | 引擎令牌 | 立即传播到全部在途引擎，终止整个进程树 |

把两者混在一个令牌上，要么达限时杀出半截归档，要么取消后排队任务还在启动。

## 6. 关机只在「非取消的正常结束」路径触发恰好一次

判断点唯一放在全部任务完成之后；取消异常向上传播时不会到达这里。
测试要显式断言 `ShutdownCalls` 的精确次数，而不是「有没有调用」。

## 7. 并发下完成顺序不等于输入顺序

结构化输出（NDJSON，逐行 JSON 事件流）的消费方必须按 `source` 字段关联条目，
不能靠行号或顺序推断是哪一项。帮助与命令行参考里专门写了这一章。

## 8. 自动化脚本测「取消」要绕开信号被忽略的坑

**2026-11-05 实测新知**：非交互 shell 启动的后台作业默认**忽略 SIGINT（中断信号）**。
直接 `kill -INT <后台PID>` 会被丢弃，压缩照常跑完返回 `0`，看起来像「取消功能坏了」，
实际是测试方式错了。前两次尝试都因此失败。

**做法**：在子进程里先重置信号处置再启动程序，例如
`zsh -c 'trap - INT; exec "$@"' _ dotnet ... &`，随后 `kill -INT` 才会被程序的
`Console.CancelKeyPress` 捕获。同时要让任务足够长（多份较大文件串行压缩），
否则信号到达时任务已经结束。

实测确认：退出码 `130`，日志记录 `Operation cancelled by user (Ctrl+C)` 与
`Operation was cancelled`，且 `pgrep -x 7zz` 查不到残留进程——
印证了「取消杀整棵进程树」这条约束确实生效。
