# 外部程序与许可经验

> 项目自己不实现压缩算法，全部交给外部命令行程序；「程序能跑起来」的第一怀疑对象是二进制定位。

## 1. 可执行文件查找要有明确的候选路径表，并逐个校验

`7zz` 的顺序是：显式配置路径 → 程序目录 `tools/7zip/<平台>/7zz` → 当前工作目录同类路径 → 系统路径
（macOS 含 `/opt/homebrew/bin/7zz`；Linux 含 `/usr/bin/7zz`；Windows 查 `Program Files/7-Zip/7z.exe`）。
每个候选都要验证存在、可执行、架构正确，失败原因写进诊断输出。
**当前核实**：`SevenZipArchiveEngine.GetCandidatePaths()` 与 `TryValidateExecutable()`。

## 2. 从访达（Finder）启动时 `PATH` 不可靠

打包脚本因此把 `7zz` 及许可证、说明、历史文件放进 `.app/Contents/MacOS/tools/7zip/macos/` 固定相对路径，
而不是指望系统 PATH。命令行里能跑通、双击应用跑不通，优先查这条。

## 3. 按目标平台（RID）复制工具，别把三份都塞进产物

csproj 用 `RuntimeIdentifier` 条件决定复制 `macos/` / `linux-x64/` / `linux-arm64/` 哪一份；
macOS 那份是通用二进制（universal，含 x86_64 + arm64）。
打包脚本会拒绝非 `Mach-O universal` 的 `7zz` 和非 arm64 的 RAR，避免装好之后才发现执行失败。

## 4. RAR 许可：不要分发「分发包的独立部分」

win.rar GmbH 协议第 3a 条禁止未经书面许可分发官方包的独立组件（UnRAR 除外），
第 3b 条禁止把未授权试用版打包进其它软件包。
**已落实的决策 B**：`tools/rarLinux/` 保存官方 `rarlinux-x64-723.tar.gz` 的**完整未修改**解包内容
（12 个文件，含 `license.txt`、`unrar`、`default.sfx` 等），Linux x64 构建整体复制，不再只挑一个 `rar`。
macOS 私有打包仍要求用户提供 `BATCHCOMPRESS_RAR_DIR` 自行注入，授权责任由用户承担。
**当前核实**：`BatchCompress.Avalonia.csproj` 的 `linux-x64` 条件块、许可风险说明文档的「决策更新」段。

## 5. 只有 `rar` 能创建 RAR，`unrar` 不行

引擎路由里「创建 rar」与「解压 rar」是两条不同路径；解压时先由 `ArchiveVolumeResolver`
判断归档种类再分派，格式字段缺失时才有回退逻辑。

## 6. 退出码 `0` 和 `1` 都可能代表成功或非致命警告

WinRAR / 7-Zip 的 `1` 常表示「有警告但完成了」，不要一律当失败；
真正需要区分的是引擎返回结构里的 `Success` 与错误消息，而不是裸退出码。
另外 `7zz` 没有「创建后自动测试」开关，成功创建后要显式再跑一次 `t` 命令，
且分卷归档必须以**实际首卷**为测试入口（基础输出文件可能不存在）。

## 7. 升级官方 `7zz` 时的最小动作

从官方发布页下载三个平台的压缩包 → 校验 SHA-256/SHA-512 → 只替换 `7zz` 与随包
`History.txt` / `License.txt` / `readme.txt`，保留仓库既有目录约定（不引入 `7zzs`、`MANUAL/`）→
确认可执行位 → 同步 README 与许可文档里的版本号和校验和。
当前仓库为 7-Zip **26.05**（macOS 通用二进制、Linux x64、Linux ARM64 三份统一）。
