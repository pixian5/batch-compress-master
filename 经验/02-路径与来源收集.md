# 路径与来源收集经验

> 这一类是本项目最容易造成「静默错误」的地方：不报异常，但生成错文件名或漏删文件。

## 1. 尾部斜杠是致命缺陷，不是小瑕疵

图形界面列表输入 `/path/to/dir/` 时，`Path.GetFileName(...)` 返回空串，
压缩输出名会变成 `.7z` 空名归档；后处理移动源目录时还会因名字为空产生自引用错误。
**做法**：所有收集出口统一经过「Trim → `GetFullPath` 转绝对 → 根路径守卫 → 去掉尾部两个目录分隔符」。
**当前核实**：`SourceCollector.NormalizePath` 即此顺序，界面与命令行共用。

## 2. 根路径必须单独守卫

`GetFullPath("/")` 还是 `/`，再去尾部斜杠会得到空串；Windows 上 `C:\` 会退化成 `C:` 盘符相对路径。
规范化函数必须先判断「等于根路径」就原样返回，再执行 `TrimEnd`。

## 3. 收集阶段不要做存在性过滤

不存在的路径交给服务层统一按「来源不存在」上报并计数，界面/命令行看到一致的结果。
收集阶段直接抛异常或静默丢弃，都会让错误提示与计数对不上。
非法字符等无法规范化的路径也原样返回，由下游处理。

## 4. 系统元数据过滤要跨平台一致，且在业务判断之前

`.DS_Store`、`Thumbs.db`、`.tmp*` 之类的过滤要在「扩展名判断」「已处理标记判断」之前执行，
否则 macOS 与 Windows 的批处理范围会不一致。已处理标记是文件名里的 `【已压缩】` / `【已解压】`。
目录批处理只扫描**直接子项**，不递归，这是刻意保持的历史口径。

## 5. 分卷组要折叠成一个任务入口，且主卷入口必须走分组逻辑

目录扫描会把分卷成员折叠到主卷，一次任务处理整组。但旧式主卷 `base.rar` / `base.zip`
本身是普通归档名，不匹配任何分卷正则，早期实现从主卷入口会退化成单卷：
解压后只删主卷、`base.r00` 等成员变孤儿，且跳过缺卷预检。
**做法**：进单卷分支前先尝试按旧式组构造结果，并从 `partN` 路径复用同一个组结果构造函数，避免逻辑漂移。
**当前核实**：`ArchiveVolumeResolver` 有对应处理；该缺陷曾被真实 `zip -s` 分卷复现并修复。

## 6. 分卷后缀的编号模型要分清

PKZIP 旧式分卷从 `.z01` 起，`.z00` 非法（曾因正则误匹配导致与主卷撞号、整组被跳过）；
RAR 的 `.r00` 是合法首分卷。编号映射不要靠 `Math.Max` 截断，主卷编号 1 要显式返回 `rar`/`zip`。
`base.part1.rar` 这类匹配正则，天然走组路径。
**教训**：加正则时把「已知不该匹配」的文件名（`data.gz`、`file.r1`、`backup.tar.2024`）也写成断言。

## 7. 密码本模式不能提前剔除空行 / Trim

密码本按「文件行、密码行」交替解析，提前去空行会破坏配对语义。
普通多行清单可以剔空行，密码本必须保留原始行序。
