# 测试与验证经验

## 1. 测试是控制台程序，不是 `dotnet test` 体系

`BatchCompress.Avalonia.Tests` 是输出 59 项检查的可执行程序，
`BatchCompress.Avalonia.sln` **只包含主项目**，必须单独指定 csproj 运行：

```bash
dotnet run --project BatchCompress.Avalonia.Tests/BatchCompress.Avalonia.Tests.csproj --nologo
```

用 `dotnet test` 或只构建解决方案，会误以为「测试跑过了」，其实一项都没执行。

## 2. 测试工程链接生产源码

csproj 关闭默认编译项，用 `<Compile Include="..\Core\**" Link="...">` 编译交付代码本身。
新增服务类后**必须**在该 csproj 登记，否则测试根本没覆盖到它——这是很容易漏的一步。

## 3. 加新功能先补断言，再动实现

「表征测试」锁的是可观察行为：消息文本、七类计数、关机时机、文件系统副作用、
取消时的临时目录残留。用脚本化假引擎（`ScriptedArchiveEngine`）控制延迟与取消时机，
覆盖「进循环前取消」「引擎执行中取消」两条路径。

## 4. 并发测试至少连跑三遍

并发缺陷常常是概率性的。批次 5 的做法是新增并发用例后重复运行三次都稳定才算通过。

## 5. 端到端夹具与单元测试是两层

`测试夹具/全功能测试/run-all-tests.sh` 覆盖真实文件系统与命令行场景（现约 149 项）；
控制台测试覆盖逻辑与边界。两者都要跑，只跑一层会漏掉真实归档行为。
官方 `7zz` 真实带密码压缩/解压、归档测试、解压后逐字节核对内容，属于关键回归项。

## 6. 改完先在小规模测试环境验证，再考虑真实目标

新代码先用测试目录、测试卷、测试数据跑通；用户没明确点名真实目标时默认用测试环境。
`--dry-run` 是安全的预检手段，只列任务、不创建输出目录、不写归档。

## 7. 收尾要验证，不要「我记得跑过了」

一轮改动的检查清单：构建 0 警告 0 错误 → 全量测试通过 → Release 构建 →
`scripts/smoke-test.sh` 秒级冒烟（多语言帮助、参数异常阻断、三平台打包自检）→
检查有无残留进程/临时目录 → 提交推送。
留下可核对的输出，不要只在脑子里确认。
