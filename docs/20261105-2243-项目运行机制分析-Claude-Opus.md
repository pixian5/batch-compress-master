# 项目运行机制分析

> 用户原问题：「你分析项目如何运行」
>
> 撰写时间：2026-11-05 22:43　模型：Claude-Opus　分析对象：仓库当前状态 `VERSION = 0.7.6`
> 本文基于实读源码（`Program.cs`、`App.axaml.cs`、`HeadlessBatchRunner.cs`、`CommandLineHandler.cs`、
> `Core/Services/**`、`Core/Services/Pipeline/**`、`ViewModels/MainWindowViewModel.cs`、
> `BatchCompress.Avalonia.csproj`、`scripts/package-macos.sh`、`README.md`）与命令行实测，
> 不引用记忆中的历史版本结论。

## 一句话结论

**一个进程、两套入口、一套共用业务层。** 真正执行压缩与解压的是外部命令行程序
（官方 7-Zip 的 `7zz`、或用户自行安装的 RAR/WinRAR）；本程序负责来源收集、参数生成、
进程调度、进度统计、日志与后处理。图形界面与命令行共用同一个 `ArchiveEngineRouter`
和 `BatchOperationService`，因此两端能力一致。

## 一、进程启动与分流

唯一入口 `Program.Main`（`Program.cs`，`[STAThread]`），判定顺序如下：

1. 过滤 macOS Finder / LaunchServices 启动时附加的 `-psn_*` 进程序列参数。
2. `--help`：在初始化 Avalonia（图形界面框架，Avalonia）之前输出对应语言帮助，退出 `0`。
   `--help` 会与 `--lang` 组合预扫描语言。
3. `--version`：读程序集 `AssemblyInformationalVersionAttribute`，输出
   `BatchCompress.Avalonia <版本>`，退出 `0`；不创建日志、不创建归档引擎。
4. `CommandLineHandler.ParseArguments`：项目自研解析器，把 `compress` / `extract` / `gui`
   动词与旧式 `--compress` / `--decompress` 开关统一规范化。失败时按本地化文案写 stderr，退出 `2`。
5. 解析成功后立刻 `LocalizationService.Instance.CurrentLanguage = options.Language`，
   让无界面运行期服务层消息（`ItemNotFound`、`ItemSucceeded` 等）与 CLI 输出语言一致。
6. `options.Compress || options.Decompress` → `RunHeadlessAsync` 同步等待
   `HeadlessBatchRunner.RunAsync()`，返回真实批处理退出码。
7. 其余 → macOS 先 `WaitForMacOsDisplayLink()` 轮询 `CVDisplayLink`（CoreVideo 显示链接口）
   连续两次成功才继续（绕开显示器唤醒/切换时建窗崩溃竞态，命令行不经过）；
   然后 `BuildAvaloniaApp().StartWithClassicDesktopLifetime()`，
   生命周期为 `ShutdownMode.OnLastWindowClose`。

**版本唯一来源链**：根目录 `VERSION` → csproj 用 `ReadAllText` 写入程序集版本 →
CLI `--version` 读程序集 → `scripts/package-macos.sh` 写入 `Info.plist` 并回读校验。
禁止在别处手写版本号。

### GUI 生命周期补充

`App.OnFrameworkInitializationCompleted` 先构造 `MainWindowViewModel`（完成语言检测），
再创建 `MainWindow` 并设为 `DataContext`，随后建立托盘并订阅
`LocalizationService.PropertyChanged`（运行中切换语言刷新文案）。

macOS 上 Avalonia 的 `TrayIcon` 实测不生成系统状态栏项，因此随应用包分发
`BatchCompress.StatusBarHelper`（Swift 原生进程，显示「压」字菜单）。
它的菜单文案在启动时固定，无法运行期改写，所以语言切换时主程序先 `Kill` 旧进程、
再带新文案（tooltip、显示/隐藏、退出）重启；非 macOS 平台则重建 `NativeMenu`。

## 二、分层与依赖方向

```
Views/MainWindow.axaml
  → ViewModels/MainWindowViewModel.cs + OperationSession
      → Core/Services/BatchOperationService（业务编排）
          → SourceCollector（来源收集，GUI/CLI 共用）
          → Core/Services/Pipeline/BatchExecutionPipeline<T>（执行管线）
              → IBatchItemAdapter<T>：CompressionItemAdapter / DecompressionItemAdapter
              → PostProcessService（删除、移动、改名）
          → ArchiveEngineRouter（格式路由）
              → SevenZipArchiveEngine / RarArchiveEngine
                  → ArchiveProcessRunner（唯一进程边界）
                      → 外部 7zz / rar / WinRAR 子进程
```

- 界面层不拼接任何 Shell 命令；`MainWindowViewModel.CompressAsync` 只做
  `SourceCollector.CollectCompressionSourcesFromText` → `BuildBatchOperationOptions` →
  `BatchOperationService.BatchCompressAsync`，进度经 `OperationSession` 回写界面。
- `HeadlessBatchRunner` 构造 `ArchiveEngineRouter`，并注入
  `BatchOperationService(_archiveEngine, new HeadlessSystemIntegration(_logger), _logger)`；
  `--output-format json` 时改用 `NdjsonOutputWriter` 输出结构化事件流。
- `BatchOperationService.BatchCompressAsync` / `BatchDecompressAsync` 分别用
  `BatchExecutionPipeline<string>` / `BatchExecutionPipeline<FileEntry>` 配对应适配器执行。
- 适配器模式把压缩与解压的条目级差异（预检、输出路径、分卷求和、失败回滚、消息文本）
  收敛到 `Pipeline/` 目录，管线骨架只负责循环、取消、计数、并发与关机。

### 外部程序定位

`SevenZipArchiveEngine.GetCandidatePaths()` 按顺序尝试：

| 平台 | 候选路径 |
| --- | --- |
| 共用 | 显式配置的可执行文件路径（`--7z-path` 类配置），命中后不再回退 |
| macOS | 程序目录 `tools/7zip/macos/7zz` → 当前工作目录同路径 → `/opt/homebrew/bin/7zz` → `/usr/local/bin/7zz` |
| Linux | 程序目录 `tools/7zip/linux-x64` 或 `linux-arm64/7zz`（按进程架构选）→ 当前工作目录同路径 → `/usr/local/bin/7zz` → `/usr/bin/7zz` |
| Windows | 程序目录 `tools/7zip/windows-x64/7z.exe` → `Program Files/7-Zip/7z.exe` |

每个候选都会 `TryValidateExecutable` 校验（存在、可执行、架构正确）。
csproj 按 `RuntimeIdentifier` 把对应平台目录 `CopyToOutputDirectory`；
`package-macos.sh` 额外把 `7zz` 放到 `.app/Contents/MacOS/tools/7zip/macos/`，
因为 Finder 启动时 `PATH` 不可靠。

RAR 侧：`ArchiveEngineRouter.CompressAsync` 仅在格式 `rar` 时走 `RarArchiveEngine`；
解压用 `ArchiveVolumeResolver.DetectArchiveKind` 判断后分派。项目不分发 RAR 二进制，
Windows 查注册表与标准安装目录，Linux/macOS 依赖系统安装或 `BATCHCOMPRESS_RAR_DIR` 注入。
本机实测为 Homebrew `RAR 7.23`（2026-06-27）。

## 三、单个任务的执行链

1. **收集来源**：三种输入（目录批处理、手工多行列表、TXT 清单/密码本）。
   `SourceCollector` 统一做去空格、`Path.GetFullPath` 规范化、消除尾部目录分隔符
   （避免 `Path.GetFileName` 返回空串生成 `.7z` 空名归档）、忽略大小写保序去重、
   过滤系统元数据文件（`.DS_Store` 等）。目录批处理只扫描直接子项。
2. **预检准备**：适配器 `PrepareAsync` 处理分卷识别与折叠、密码读取、输出路径解析、
   已存在文件策略、缺卷阻断；跳过或失败时自行更新计数并上报进度。
3. **调用引擎**：`ArchiveProcessRunner` 用 `ProcessStartInfo.ArgumentList` 逐项传参，
   `UseShellExecute=false`、`RedirectStandardOutput/Error=true`；
   stdout/stderr 用两个 `ReadToEndAsync()` 并行读取防止管道阻塞；
   取消时 `Kill(entireProcessTree: true)` 并等待退出。
   7zz 没有「创建后自动测试」开关，因此成功后显式执行 `t` 命令，且分卷须以实际首卷为入口。
4. **后处理与进度**：`PostProcessService.Apply` 统一做删除/移动/改名；
   归档成功与后处理成功分别计数，避免「归档成功但移动失败」被显示为完全成功。
   失败项单独计数并回滚残留文件。

### 并发、取消、大小上限与关机

- `MaxConcurrency > 1` 且条目多于 1 → `RunConcurrentAsync`：信号量限流，
  进度统计与上报经同一把锁保护并输出克隆快照（防撕裂读）。否则走串行路径。
- 大小上限（`MaxSizeGB`）由独立闸门令牌阻止**未启动**任务排队，不杀在途引擎。
- 外部取消经联动令牌传播到全部并发引擎；取消异常向上传播，绝不触发关机。
- 系统关机只在非取消的正常结束路径触发恰好一次。

### 退出码与日志

| 退出码 | 含义 |
| --- | --- |
| 0 | 成功（含 `--help` / `--version` / `--dry-run` 正常结束） |
| 1 | 任务失败或无可用归档引擎 |
| 2 | 参数错误、密码解析失败、来源路径校验失败 |
| 130 | Ctrl+C 协作式取消（`Console.CancelKeyPress` → `cts.Cancel()`） |

日志为 `batchcompress_<时间戳>.log`，多代轮转：第 1 代 `.log.1` 保持纯文本，
第 2 代起为 `.log.<代次>.gz`（Gzip），默认 5 代、权限 0600、过期清理默认 7 天且可配
（`--log-retention-days`）。**归档子进程参数与原始输出含明文密码，明确不脱敏**，
日志不得作为可公开数据处理。

## 四、构建、测试与发布运行

```bash
dotnet restore
dotnet build BatchCompress.Avalonia.sln --nologo            # 仅含主项目
dotnet run --project BatchCompress.Avalonia.csproj --no-build -- compress -i ./data -o ./out -e 7z --dry-run
dotnet run --project BatchCompress.Avalonia.Tests/BatchCompress.Avalonia.Tests.csproj --nologo
```

- 目标框架 `net10.0`，`OutputType=WinExe`，编译绑定默认开启
  （`AvaloniaUseCompiledBindingsByDefault=true`）。刻意不引用 `Avalonia.Diagnostics`。
- 测试是控制台程序（当前 59 项检查），以 `<Compile Include>` 链接生产源码，
  **不在 `.sln` 内**，必须单独指定 csproj，不能只用 `dotnet test`。
- macOS 发布：`scripts/package-macos.sh` → `dotnet publish -c Release -r osx-arm64
  --self-contained true -p:PublishSingleFile=true` → `swiftc` 编译状态栏帮助进程 →
  组装 `.app`（Contents/MacOS、Info.plist、icns、tools/7zip）→ `codesign` →
  装到 `/Applications`（`--dist` 只产出 `.app.zip`）。自包含，不依赖本机 .NET 运行时。
  不要用 `open -n` 启动，会在 Dock 最近使用留下重复记录。
- 另有 `package-linux.sh` / `package-windows.sh` / `package-all.sh` 与
  `.github/workflows/release.yml`（`v*` tag 触发三平台发布）。

## 六、发现的问题与建议（未改动，供决策）

1. **README「文档」小节链接过期**：`README.md` 第 106-108 行仍指向
   `docs/20260930-0107-当前开发进度-未标注.md` 等旧文件，而 `docs/` 已有
   `20261104-1155-当前开发进度-Antigravity.md` 等最新文档。README 顶部
   【当前开发进度】【下一步待实现】章节本身是最新的，仅「文档」小节索引陈旧，建议同步。
2. **根目录 `经验/` 目录尚未创建**：既定要求是把 `docs/` 全部文档分类整理为简洁经验 md。
   当前 `docs/` 有 69 篇、`文档/` 有 91 篇，一次性整理属于独立工作量，建议单独一轮处理，
   避免与分析任务混在一起产生未经核对的结论。
3. **RAR 许可注意**：csproj 在 `linux-x64` 构建时会整体复制 `tools/rarLinux/**`
   （批次 3 决策 B：完整未修改官方分发包），对外分发仍需留意 win.rar GmbH 许可条款；
   macOS 打包要显式设置 `BATCHCOMPRESS_RAR_DIR`。
4. **日志含明文密码**：属既定诊断行为，但任何日志外发、公开 Issue 附件或 CI 产物上传
   前必须人工确认，建议在 CI 发布流程里加一条显式提示。

## 结论

项目运行模型是「薄界面 + 厚编排 + 外部二进制」：入口判定极早返回、GUI/CLI 共用内核、
外部程序调用收敛到单一进程边界、指标体系与日志贯穿全程。
理解排障路径时，优先看 `batchcompress_*.log` 里的完整命令行与原始 stdout/stderr，
再沿 `ArchiveEngineRouter` → 具体引擎 → 候选路径表定位二进制问题。
