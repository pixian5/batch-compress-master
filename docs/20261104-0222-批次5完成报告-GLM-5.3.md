## 2. 并发设计说明（BatchExecutionPipeline，219 → 416 行）

### 2.1 分派原则

`RunAsync` 入口分派：`MaxConcurrency > 1 且条目数 > 1` 进入 `RunConcurrentAsync`，
否则走 `RunSequentialAsync`（批次 2 阶段 1 原实现逐字节保留，17 项表征测试继续零漂移）。
默认 `MaxConcurrency=1` 保证绝对向后兼容。

### 2.2 双令牌分离（本设计的关键决策）

| 令牌 | 联动 | 用途 | 达限时的行为 |
| :--- | :--- | :--- | :--- |
| `gateCts` | 外部取消 **或** 大小达限 | `semaphore.WaitAsync(gateCts.Token)`——闸门 | 未启动任务立即放弃（等价串行 `break` 后剩余项不执行） |
| `engineCts` | 仅外部取消 | 传给 `adapter.ExecuteAsync` 的引擎令牌 | **不影响**——在途压缩/解压自然完成，不产生半途废档 |

排队任务的退出是 `return`（正常完成）而非异常，因此 `Task.WhenAll` 只在外部取消
（引擎抛 `OperationCanceledException`）或真实异常时向上传播——"达限正常结束"与
"取消异常传播"两种语义天然分离，无需 catch 歧义处理。

### 2.3 锁的粒度

- **锁内**：`PrepareAsync` 调用（适配器契约内为 `Task.FromResult` 同步实现，
  `GetAwaiter().GetResult()` 不阻塞，直接回写共享进度对象必须互斥）、
  启动消息、`ReportArchiveOutput`、完成段统计与消息、`processedSizeGB` 累加、
  达限检查与上报——`progressInfo` 与累计量的全部读写都在同一把 `gate` 锁内；
- **锁外并发**：引擎调用（真正耗时段）、`MeasuredBytes`（读取条目私有状态）、
  后处理 `PostProcessService.Apply`（对不同目标的文件删除/移动互不共享）；
- **上报口径**：并发路径统一 `Report(CloneProgress(progressInfo))` 克隆快照
  （新增按当前状态克隆的重载，与串行路径共用同一实现，字段口径一致）——
  CLI NDJSON（`StringWriter` 非线程安全）因此被管线锁天然串行化。

### 2.4 每条目执行顺序

准备（锁内）→ 启动消息（锁内）→ 引擎（锁外，engineCts）→ 命令输出转发（锁内）→
测量+后处理（锁外）→ 统计与消息（锁内，含达限检查）→ 释放信号量。
串行路径的消息语义（ItemSucceeded / ItemSucceededWithPostProcessFailure / ItemFailed、
七类计数、SizeLimitReached）在并发路径逐条对应保留。

### 过程缺陷与经验记录（如实记录）

- **CLI 透传一度缺失**：向 `HeadlessBatchRunner` 注入透传时的文本锚点
  （`SkipProcessed`）与实际属性名（`SkipAlreadyProcessed`）不符，脚本替换**静默未生效**，
  首轮 CLI 冒烟因此实际走串行路径仍"功能通过"。最终核对 `git status` 变更清单时发现
  该文件未变更，修复后以"串行/并发耗时对比"这种能区分串并行的观测方式复测确认。
  经验：① 脚本化文本替换必须断言命中；② 并发功能的冒烟必须包含**可区分串行与并发**
  的证据（耗时对比或并发峰值），仅"功能成功"无法证明并发生效。

## 5. 已知边界（移交批次 6 或后续）

1. **并发下消息顺序**非确定（完成顺序驱动），GUI 逐项日志顺序与串行不同——
   计数与每条消息内容本身精确；NDJSON 消费方不应假设顺序（文档已注明）；
2. `MaxConcurrency` 为机器级参数，未纳入页签状态持久化（有意：两页签共享）；
3. 高并发写同一输出目录时 Windows 下的短文件名/锁竞争依赖引擎自身行为，未做额外串行化。
