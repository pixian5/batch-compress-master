## P0 · 发布可用性与合规（优先，影响真实用户能否用上）

### P0-1　macOS 正式签名、公证与硬化运行时

- **现状**：`scripts/package-macos.sh:130` 是 `codesign --force --deep --sign -`（ad-hoc 临时签名）；
  无 Developer ID、无公证（notarization）、无 hardened runtime 与 entitlements。
- **不改会怎样**：用户从 GitHub Release 下载 `.app.zip` 会被 Gatekeeper 拦截，
  必须手动「右键→打开」或执行 `xattr -d com.apple.quarantine`；macOS 分发实质不可用。
- **改动点**：`scripts/package-macos.sh` 增加可选签名模式（有证书时走 Developer ID +
  `--options runtime` + entitlements，无证书时回退 ad-hoc 并打印醒目提示）；
  `--dist` 流程里加 `xcrun notarytool submit` / `stapler staple`（可用开关跳过）；
  `.github/workflows/release.yml` 用仓库机密注入证书与公证凭据；
  README 写清「正式签名版」与「自签名版」的区别。
- **验收**：在一台干净的 macOS 机器上下载 Release 的 `.app.zip`，
  解压后双击能直接启动、无 Gatekeeper 拦截；`spctl -a -vv` 与 `codesign --verify --deep --strict` 通过。
- **风险/依赖**：需要 Apple Developer 账号（付费）与证书，CI 机密要妥善保管；
  若暂不投入，至少先落地「README 写明绕过方法」的降级方案。
- **版本**：改脚本与工作流，不改产品 `.cs`，按现行口径不触发加版本（若判定脚本也算源码则 +0.0.1，需先确认口径）。

### P0-2　Release 校验和清单与产物安全扫描

- **现状**：`release.yml` 的产物核对只 `test -f` 三个归档是否存在；无 SHA-256 清单；
  没有检查产物里是否混入日志。
- **改动点**：`release.yml` 的 `release` 作业在上传前生成 `SHA256SUMS.txt` 并一并上传；
  增加一步扫描：解包抽查三个产物，若出现 `batchcompress_*.log*`、`*.log`、`enclosures.txt`
  或疑似凭据文件则失败；README 增加校验命令示例（`shasum -a 256 -c SHA256SUMS.txt`）。
- **验收**：一次预发布演练里，故意在产物目录放一个假日志文件，工作流必须红；
  移除后生成清单且本地校验通过。
- **风险**：扫描规则误报（例如合法的文件名），先用白名单方式实现。
- **版本**：仅工作流与文档，不加版本。

### P0-3　RAR 分发合规复核与「不含 RAR」发行版

- **现状**：`BatchCompress.Avalonia.csproj` 在 `linux-x64` 条件复制 `tools/rarLinux/**`
  （官方完整未修改分发包，实测 11 文件）到产物；`release.yml` 把 Linux `.tar.gz` 传到公开 Release。
  许可说明文档记录了第 3 条（完整未修改可分发）、第 3a 条（不得分发独立部分）、
  第 3b 条（未授权试用版不得打包进其它软件包）。
- **不改的后果**：对外分发的合规边界未确认；若被认定为「打包进其它软件包」，存在下架/追责风险。
- **改动点**：先把适用条款的结论写进 `docs/20260929-2351-RAR二进制许可风险说明-未标注.md`
  的「决策更新」段；`scripts/package-linux.sh` 增加 `--no-rar` 选项产出不含 RAR 的发行版；
  `release.yml` 默认上传不含 RAR 版，完整版作为可选附件并附醒目许可说明；
  README 明确两种发行版的差别。
- **验收**：两种 Linux 产物都能构建，`--no-rar` 版内 `find` 不到 `rar`/`unrar`；
  7z/ZIP 功能在两版都正常，RAR 功能只在完整版可用且提示用户自行确认授权。
- **风险**：需要法务层面判断，本文不下结论；与 P2-10 的平台能力一致性一起处理更省事。
- **版本**：改脚本/工作流不改产品 `.cs`；若同时改运行时提示文案则按口径判定。

## P1 · 正确性与持续集成门禁（防止回归与静默错误）

### P1-4　取消或异常时清理在途归档

- **现状/证据**：`Core/Services/Pipeline/CompressionItemAdapter.cs:236` 的 `OnExecutionFailed`
  是空实现，注释写「压缩失败没有输出回滚需求」；`ExecuteAsync` 的 `finally` 只删附件暂存目录。
  取消是抛 `OperationCanceledException`，不会走 `OnExecutionFailed`。
  上一轮实测：3 个任务按 Ctrl+C 后输出目录留下 1 个产物。
- **不改会怎样**：留下不完整或已写出的归档；下次用 `--existing skip` 会把它当成「已完成」跳过，
  用户以为文件已压缩好，属于**静默数据错误**。
- **改动点**：压缩引擎写目标前先写临时名（如 `.文件名.7z.tmp`），
  成功后原子 `File.Move(overwrite)` 为正式名；在 `ExecuteAsync` 的 `catch`/`finally` 里
  检测取消或异常并删除该临时文件；分卷场景要按实际首卷与全部成员一起清理。
  补充表征测试：取消后输出目录为空、成功路径文件名不变、分卷取消无残留成员。
- **验收**：`测试夹具/经验验证/verify.sh` 的取消用例增加「输出目录零残留」断言并通过；
  新增 3 项以上单元测试覆盖取消/失败/分卷；59 项原有测试零回归。
- **风险**：`7zz` 的分卷命名与临时名策略需要对齐，不能破坏分卷识别；改前先备份测试数据。
- **版本**：改产品源码，实施后 `+0.0.1`。

### P1-5　锁定 SDK 与依赖版本

- **现状**：无 `global.json`、无 `packages.lock.json`；
  `ci.yml:33` / `release.yml` 用 `dotnet-version: '10.0.x'`；本机 SDK 10.0.403。
- **不改会怎样**：云端与本机可能用不同 SDK/传递依赖构建，
  出现「本地过、CI 挂」或反之；与「本机与服务器不要混用」的要求相冲突。
- **改动点**：新增 `global.json` 锁定 `10.0.403`（或团队约定的版本）与 `rollForward` 策略；
  主项目与测试项目启用 `RestorePackagesWithLockFile=true` 生成并提交 `packages.lock.json`；
  两个工作流的 `setup-dotnet` 改为读取 `global.json`（`global-json-file: global.json`）。
- **验收**：清掉 `obj/` 后在三平台 CI 还原成功且锁文件无变更；
  故意改坏锁文件能让 CI 失败；本机 `dotnet --version` 与 CI 日志一致。
- **风险**：升级 SDK 时要同时改 `global.json` 与 CI，容易漏；写进重构指南。
- **版本**：配置文件改动，不加版本。

### P1-6　把本地三层测试资产接进持续集成

- **现状**：`ci.yml` / `release.yml` 只跑 59 项控制台测试。
  `scripts/smoke-test.sh`、`测试夹具/经验验证/verify.sh`（16 项）、
  `测试夹具/全功能测试/run-all-tests.sh`（149 项）都只在本地跑过。
- **改动点**：在 `ci.yml` 的 `build-test` 作业里，三平台都跑冒烟脚本；
  16 项实测脚本至少在 macOS 跑（它依赖本机 `7zz`、权限与 `stat -f`），
  其余平台用 `SKIP_CANCEL_TEST=1` 或做平台适配后跑；
  149 项端到端夹具作为独立作业或发布前置作业；`release.yml` 的 `test-gate` 复用同一批步骤。
- **验收**：故意在某一个用例里制造失败，CI 必须红；正常提交三平台全绿；
  发布门禁包含这三层，缺一不放行。
- **风险**：16 项脚本有 macOS 专属判断（`stat -f`、`pgrep -x`、`zsh`），跨平台需适配；
  149 项夹具耗时较长，可只在发布门禁跑。
- **版本**：工作流改动，不加版本。

### P1-7　目标平台产物的实机验证

- **现状**：`release.yml` 的 `package-cross` 在 `ubuntu-latest` 上交叉打包 Linux 与 Windows，
  只核对文件存在，从未在对应系统运行过产物。
- **改动点**：新增 `verify-artifacts` 作业，在 `windows-latest` 与 `ubuntu-latest`
  下载各自产物并至少执行 `--version`、一次真实压缩→解压往返、核对内容一致；
  macOS 作业同样做一次（可用现有 16 项脚本的子集）。
- **验收**：故意放入错误架构的 `7zz`，对应平台的验证必须失败；
  正常发布时三个平台各有一条「产物可运行」的绿色记录。
- **风险**：Windows runner 上 `7zz` 定位逻辑查的是 `7z.exe` 与 `Program Files`，
  需要确认产物里确实带了可用二进制，否则先补资源再验证。
- **版本**：工作流改动，不加版本。

## P2 · 可维护性（降低后续每次改动的成本）

### P2-8　本地化资源外置并补齐日文/德文帮助

- **现状**：`LocalizationService.cs` 1,667 行，五种语言各一个约 290 行的 `Create*()` 方法；
  `CommandLineHandler.cs` 另有 3 套帮助文本常量，`GetHelpText` 把 `ja`/`de` 回退英文。
  两套文案源独立维护，容易漂移；`AvailableLanguages` 与服务层是五语言，帮助只有三语言。
- **改动点**：把五套字典外置为 `.resx` 或 JSON 资源（项目已引用 `System.Resources.Extensions`），
  `LocalizationService` 改为按语言键加载；帮助文本也纳入同一套资源或至少抽出独立文件；
  新增 `JapaneseHelpText` / `GermanHelpText` 常量或资源条目，`GetHelpText` 补两条分派；
  扩展现有「英文与德语资源不含中文」「界面本地化资源扫描」测试，
  增加「五种帮助文本都含全部选项名」的一致性断言。
- **验收**：`--lang ja --help` 与 `--lang de --help` 输出对应语言而非英文；
  59 项测试全过且新增一致性测试通过；加一种新语言只需加一个资源文件。
- **风险**：改动面大，必须先补表征测试锁住现有五语言文案；建议一个批次只做「资源外置」，
  下一批次再做「帮助补齐」，避免一次改太多。
- **版本**：改产品源码，实施后 `+0.0.1`（若拆两批则各加一次）。

### P2-9　拆分超千行文件

- **现状**：测试工程 `Program.cs` 3,692 行、`MainWindowViewModel.cs` 1,491 行、
  `MainWindow.axaml.cs` 789 行、`CommandLineHandler.cs` 1,299 行。
- **改动点**：测试按领域拆成多个分部类文件（CLI / 引擎 / 本地化 / 管线 / 日志）；
  ViewModel 按「来源与目标」「压缩选项」「解压选项」「日志与状态」拆分部类；
  `MainWindow.axaml.cs` 里能下沉到 ViewModel 的逻辑下沉；
  `CommandLineHandler` 把帮助文本与解析逻辑分离（与 P2-8 协同）。
- **验收**：拆分前后 59 项测试零回归、消息文本与计数零漂移（沿用批次 0-6 的表征测试做法）；
  单文件行数降到 800 以下。
- **风险**：纯重构无功能变化，风险主要在绑定与编译绑定；
  项目是开发测试版，无需兼容旧数据，但改前先备份。
- **版本**：改产品源码，实施后 `+0.0.1`。

### P2-10　Linux x64 与 ARM64 的 RAR 能力一致性

- **现状**：csproj 只在 `linux-x64` 条件复制 `tools/rarLinux/**`；ARM64 产物只有 `7zz`。
  `RarArchiveEngine.GetLinuxCandidates()` 首选 `AppContext.BaseDirectory/tools/rarLinux/rar`，
  在 x64 上已生效（早期记忆中的「死路径」已失效）。用户文档没有说明这种差异。
- **改动点**：明确产品决策——ARM64 是「不支持内置 RAR」还是「需要官方 ARM64 分发包」；
  在 README、快速参考、跨平台评估里写清；运行时若 RAR 不可用，给出可操作的提示
  （当前提示容易让人误以为是路径配置问题）。
- **验收**：在两个架构的 Linux 产物上分别运行 `--version` 与 RAR 创建尝试，
  ARM64 得到明确、本地化的能力说明；文档与行为一致。
- **风险**：与 P0-3 的合规结论相关，建议一并决策。
- **版本**：若改提示文案或路由，改产品源码则 `+0.0.1`。

## P3 · 体验演进（按需排期）

### P3-11　分卷压缩实时子进度

- **现状**：现有待办第 1 条；进度以「条目」为粒度，分卷压缩时一个大任务会长时间停在同一个百分比。
- **改动点**：解析 `7zz` / RAR 的 stdout 中分卷切换信息，换算为子进度；
  经 `OperationProgressInfo` 上报，界面与 NDJSON 同时可见；ETA 复用 `OperationSession` 的均速兜底。
- **验收**：多卷压缩时进度条平滑推进；并发下不串项；`--output-format json` 的子进度事件可被消费。
- **风险**：外部程序输出格式随版本变化，要做「解析失败就回退到条目级进度」的降级，不能因解析失败中断任务。
- **版本**：改产品源码，`+0.0.1`。

### P3-12　NDJSON 机器可读契约与诊断导出

- **现状**：`文档/COMMAND_LINE.md` 有 NDJSON 事件类型的文字说明，但没有机器可读的
  schema（数据结构定义）与版本字段；消费者只能靠文档推断字段。
  另外排障时用户需要手工找日志文件，而日志含明文密码。
- **改动点**：新增 `docs/ndjson-schema-v1.json`（或仓库内 `schemas/`），
  在 summary 事件里加 `schemaVersion`；写一致性测试保证事件字段与 schema 匹配；
  提供「导出诊断」命令，打包最近 N 代日志时**明确提示含明文密码并要求确认**，
  默认排除密码本文件内容。
- **验收**：用 schema 校验一次真实压缩的事件流全部通过；字段变更必须同步升 `schemaVersion`；
  导出功能在用户未确认时不产生文件。
- **风险**：**绝不能改成自动脱敏日志**（用户明确选择的诊断行为），只在「导出/外发」环节做提示与确认。
- **版本**：改产品源码，`+0.0.1`。
