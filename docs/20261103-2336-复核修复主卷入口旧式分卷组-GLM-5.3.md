# 复核修复：主卷入口的旧式分卷组识别

日期：2026-11-03 23:36
版本：`0.6.8`（对 `0.6.7` 批次 1 的复核修复）
模型：GLM-5.3

## 复核结论

对 `0.6.7` 旧式分卷实现做逐路径批判性复核（正则误匹配边界、模式互斥性、编号模型、大小写交互、统计语义、测试的文件系统兼容性），发现一个真实缺口，其余设计确认无误。

## 发现的缺口

`Resolve()` 的单卷优先分支（存在同名单卷且文件名不匹配任何分卷正则时直接返回单卷）与旧式分卷的命名结构冲突：旧式主卷 `base.rar` / `base.zip` 本身就是普通归档名，永远不匹配分卷正则。因此**从主卷入口解析时退化为单卷结果**：

- `FilesForPostProcessing` 只含主卷 → 解压后勾选"删除/移动源文件"只处理主卷，`base.r00`、`base.z01` 等成员遗留成孤儿文件；
- 分卷组完整性预检（缺卷、编号重复）被跳过。

图形界面目录扫描的任务入口正是主卷（成员折叠到主卷），所以该缺口影响主流程。`0.6.7` 的实测只覆盖了从 `.z01` 成员入口的路径（先归组再折叠，正确），恰好漏掉主卷入口。

## 修复方案

1. `Resolve()` 进入单卷分支前调用新增的 `TryBuildOldStyleGroupResult`：主卷扩展名为 rar/zip 且同目录存在分卷成员（组内编号 ≥ 2）时，按旧式组返回整组结果；只有主卷、没有成员时维持单卷语义，普通归档行为不变。
2. 组结果构造提取为 `BuildGroupResult`，`Resolve` 主路径与旧式主卷入口共用，保证两条路径的重复编号、首卷与缺卷判定完全一致，避免逻辑漂移。

## 语义变化（有意为之）

- 主卷入口现在返回整组：解压后删除/移动源覆盖全部成员；组不完整（如缺 `.r01`）时在预检阶段报缺跳过，而不是把错误推迟给 rar/7zz 引擎。
- 与 part 分卷现状的差异说明：`base.part1.rar` 匹配分卷正则、天然走组路径；旧式主卷此前走单卷路径是命名结构导致的行为缺口，本次对齐。
- 已知边界：同目录同 base 名的 `.rNN`/`.zNN` 文件视为分卷成员（与 rar/WinRAR 自身的卷查找约定一致）；极罕见的"无关文件恰好命名为 base.r00"会被并入组并在后处理中一并删除。
