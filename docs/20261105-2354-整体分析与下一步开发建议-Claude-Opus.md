## 一、结论摘要

项目**工程质量扎实、功能完整度高于一般开发测试版**：分层清晰、双入口共用内核、
59 项单元测试 + 16 项端到端实测 + 149 项夹具 + 冒烟脚本、三平台持续集成与标签发布流都在，
源码里没有 TODO/FIXME 残留，注释规范且说明动机。

瓶颈已经不在「还要做什么功能」，而在四处：

1. **发布可用性**：macOS 只做临时签名（ad-hoc，自签名），没有开发者证书与公证（notarization），
   用户下载 `.app.zip` 会被系统拦截；Release 也没有校验和清单供核对。
2. **合规边界**：Linux 发布包随附官方 RAR 完整分发包，许可条款需要复核；
   日志含明文密码是既定取舍，但发布链路没有防外泄检查。
3. **可复现构建**：没有 `global.json`、没有依赖锁文件，持续集成用浮动 SDK 版本，
   本机 10.0.403 与云端可能不一致——这与「本机与服务器不要混用」的要求相冲突。
4. **本地已有测试资产没接进持续集成**：`scripts/smoke-test.sh`、
   `测试夹具/经验验证/verify.sh`（16 项）、`测试夹具/全功能测试/run-all-tests.sh`（149 项）
   都只在本地跑，CI 与发布门禁只跑 59 项单元测试。

建议顺序：**P0 发布可用与合规 → P1 正确性与门禁 → P2 可维护性 → P3 体验演进**。
具体任务、改动点、验收标准见 [下一步待实现](20261105-2354-下一步待实现-Claude-Opus.md)。

### 架构与运行

`Program.Main` 早判定分流 → 图形界面 / 无界面两条入口共用

界面层不拼 Shell 命令；取消杀整棵子进程树；并发用双令牌分离「大小上限」与「用户取消」。
完整链路见 [项目运行机制分析](20261105-2243-项目运行机制分析-Claude-Opus.md)。

## 三、按域分析

### 3.1 架构与可维护性：结构好，但两处集中度过高的成本在上升

分层与依赖方向清楚，批次 0-6 的重构已经把 `BatchOperationService` 从 1020 行降到 425 行。
剩下的集中度主要在**文案**：`LocalizationService.cs` 里五种语言各自一个约 290 行的
`Create*()` 方法，新增一种语言要同时改 `AvailableLanguages` 字典、`switch` 分派、
`LanguageStrings` 属性（如有新词条）与五个方法；而 `CommandLineHandler.cs` 里又独立维护
三套帮助文本常量。**两套文案源容易漂移**，且 `GetHelpText()` 的分派只有
`"zh-TW" => 繁中`、`null/"zh-CN" => 简体`、`_ => 英文`，
所以 `--lang ja` / `--lang de` 拿到的是英文帮助——服务层却是五语言。
`smoke-test.sh` 只检查这些命令「不报错」，检查不出回退成英文。

### 3.2 测试与质量：资产很全，但只用了最上面一层

本地有四层验证：59 项控制台测试、16 项经验实测、149 项端到端夹具、冒烟脚本。
然而 `ci.yml` 与 `release.yml` 的门禁只跑第一层。
`测试夹具/经验验证/verify.sh` 已经能覆盖真实带密码压缩解压往返、退出码、
试运行边界、Ctrl+C 130、日志权限等——这些恰恰是最容易回归、单元测试又覆盖不到的部分。
把它们接进 CI 的边际成本很低，收益很高。

交叉编译的 Linux / Windows 产物只在 `ubuntu-latest` 上打包，
**没有在目标平台实际运行过**；发布门禁只验证「文件存在」。

### 3.3 发布：流水线齐了，但「能下载」不等于「能打开」

`scripts/package-macos.sh` 第 130 行是 `codesign --force --deep --sign - "$app_path"`，
即 ad-hoc 临时签名。没有 Developer ID 证书、没有公证、没有 hardened runtime 与 entitlements。
从 GitHub Release 下载的 `.app.zip` 在别的 Mac 上会被 Gatekeeper 拦截，
普通用户需要手动「右键→打开」或执行 `xattr -d com.apple.quarantine` 才能用。
对一个面向三平台分发的桌面工具，这是**当前最影响真实可用性的问题**。

另外 Release 附件没有 SHA-256 校验清单，用户无法核对下载完整性；
`release.yml` 的产物核对只检查三个文件存在。

### 3.4 合规与安全：既定取舍要守住边界，新增风险要复核

- 日志保留归档命令与原始输出、**含明文密码且不脱敏**，是用户明确选择的诊断行为，
  **不建议改**。要做的是保证它不外泄：`.gitignore` 已忽略 `logs/`，
  但发布流程缺少一道「产物中不得含日志文件」的扫描。
- `tools/rarLinux/` 已是官方完整未修改分发包，但 `linux-x64` 构建会整体复制，
  且 `release.yml` 把 Linux 产物上传到公开 Release。win.rar GmbH 许可第 3b 条涉及
  「未授权试用版不得打包进其它软件包」，第 3 条允许的是「完整且未修改的分发包」。
  两者如何适用需要**法务层面复核**，本文不下结论；可考虑提供不含 RAR 的发行版。
- `PasswordUtility` 用 MD5 派生是兼容旧归档的历史包袱，不是密码学保护，文档已说明。

## 五、需要你拍板的三件事

**1. macOS 正式签名与公证要不要做。**
现在的情况：应用能在本机签名并安装，但别人从 GitHub 下载会被系统拦截，需要手动绕过。
不改的后果：三平台发布里 macOS 这条实际上只适合开发者自测。
三个选项：① 接入 Apple Developer 账号（年费）＋ Developer ID 证书＋公证，CI 里用机密证书签名；
② 只做 ad-hoc 签名，但在 Release 说明里写清「需右键打开/移除隔离属性」；
③ 暂不分发 macOS 包，只保留源码构建。
**我的推荐是 ①**：项目已有完整打包与发布流水线，补签名与公证是临门一脚；
若暂时不想投入账号，先用 ② 把说明写清楚，避免用户以为程序坏了。

**2. RAR 随 Linux 产物分发怎么处理。**
选项：① 维持现状（完整未修改官方包）并做一次许可复核、把结论写进风险文档；
② 提供一个「不含 RAR」的 Linux 发行版作为默认，完整包单独可选；
③ 完全不随产物分发 RAR，只依赖用户自行安装。
**推荐 ②**：既保留开箱即用的 RAR 能力，又给合规上保险；③ 会牺牲 Linux x64 的现有能力、
且与「x64 自带、arm64 不自带」的不一致问题一起解决。

**3. 日志明文密码的边界。**
这是你明确选择的诊断行为，我不会去加脱敏。需要确认的只是：
是否同意在 CI 加一道「产物/附件中不得出现 `batchcompress_*.log*`」的扫描，
以及 Release 说明里保留「日志不可公开」的醒目提示。这属于防外泄，不是改行为。
