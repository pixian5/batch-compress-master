## 一、任务背景

在前期架构体检与实测（P1-4）中发现：
1. **压缩中途取消或失败残留不完整文件**：原 `Core/Services/Pipeline/CompressionItemAdapter.cs` 中的 `OnExecutionFailed` 为空实现（注释写「压缩失败没有输出回滚需求」）；而在用户按下 Ctrl+C、中途取消任务或发生异常（如磁盘满、子进程被杀）时，`7zz` 或 `rar` 可能在输出目录留下半成品的归档文件、分卷片段或 `.tmp` 临时文件；
2. **引发跳过机制静默数据损坏**：若留下不完整或损坏的归档，用户下次执行包含 `--skip-processed` 或 `--existing skip` 的批处理时，程序会误判该归档已完成而跳过该源文件，导致源文件未真正被备份压缩，属于极严重的**静默数据损坏/丢失风险**；
3. **解压取消缺乏管线级回滚保障**：虽然 `DecompressionItemAdapter` 实现了解压失败回滚，但若管线在 `ExecuteAsync` 外部因 `OperationCanceledException` 中断，未在最外层捕获并统一触发适配器回滚。

## 二、交付内容清单

### 1. 压缩适配器输出快照与在途残片原子回滚（`CompressionItemAdapter`）
- **执行前预置快照（`SnapshotOutputFiles`）**：
  - 在执行 `_archiveEngine.CompressAsync` 之前，通过 `ArchiveVolumeResolver.ResolveOutputFiles` 扫描目标路径、基础归档名以及所有可能的新旧分卷组；
  - 针对 `7zz` 运行期生成的 `<outputPath>.tmp`、`<name>.tmp*` 等工作临时文件，同样纳入快照扫描，记录执行前已存在的文件集合；
- **失败与取消全覆盖清理（`CleanupFailedCompressionOutput`）**：
  - 在 `ExecuteAsync` 发生异常（`OperationCanceledException`、IO 异常等）或返回 `result.Success == false` 时，精准清理所有在本次执行中新增的归档主文件、分卷碎片（`.001`、`.part1.rar` 等）与 `.tmp` 临时文件；
  - 严格保留执行前已存在的无关文件与既有旧文件，实现安全与彻底的清理平衡；
  - 正式实现 `OnExecutionFailed(PreparedBatchItem item)` 虚方法，接入泛型管线生命周期。

### 2. 泛型批处理管线取消与异常兜底（`BatchExecutionPipeline`）
- 在 `BatchExecutionPipeline.cs` 的核心执行段，增加对 `_adapter.ExecuteAsync(item, engineCts.Token)` 的统一异常拦截：
  ```csharp
  ArchiveResult result;
  try
  {
      result = await _adapter.ExecuteAsync(item, engineCts.Token);
  }
  catch (Exception)
  {
      _adapter.OnExecutionFailed(item);
      throw;
  }
  ```
- 确保在任务被外部取消（`engineCts.Cancel()`）或进程中断抛出 `OperationCanceledException` 时，适配器的 `OnExecutionFailed` 必被触发，彻底封堵在途文件残留漏洞；
- 解压循环适配器（`DecompressionItemAdapter.cs`）同步对齐该清理防护。

### 3. 测试套件扩充（59 → 62 项）与实测断言收严
