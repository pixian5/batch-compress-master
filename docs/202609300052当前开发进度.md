## A+B 批次：服务层诊断日志可见性修复（两种方案都实施）

背景：`BatchOperationService` 的 `Log()` 依赖构造函数注入的 `ILogger`，但 GUI 与 CLI 入口都未传入，导致“删除源失败”“移动源失败”“解压归档目标已存在，已保留整组源卷”等诊断不会出现在任何地方；界面只显示“成功但后处理失败: X”，用户看不到原因。经对比两种方案（注入 logger / 原因进入进度消息）后决定两者都做：日志面向事后排查，进度消息面向即时可见。

1. **方案 A：入口注入 logger**
   - GUI 入口：`MainWindowViewModel` 创建 `FileLoggerService`（设计模式跳过），日志写入 `ApplicationData/BatchCompress.Avalonia/logs/batchcompress_gui_yyyyMMdd_HHmmss.log`，并作为第三参数注入 `BatchOperationService`。
   - CLI 入口：`HeadlessBatchRunner` 把已有 `FileLoggerService` 实例同时传给 `HeadlessSystemIntegration` 与 `BatchOperationService`。
   - 效果：服务层 `Log(LogLevel.Warning/Error/…)` 全部有落点，可事后排查。
2. **方案 B：原因进入失败记录**
   - 后处理失败原因改为随逐项进度消息上报：`RecordPostProcessFailure` 先写警告日志再返回本地化消息，压缩/解压循环把原因并入最终项消息 `ItemSucceededWithPostProcessFailure`（“成功但后处理失败: {0}（原因：{1}）”）。
   - `TryMoveWithoutOverwrite` 增加 `out string failureReason`，区分“目标已存在（已保留双方）”与“移动异常”。
   - 新增 8 个 PostProcess 词条 × 5 语言（目标已存在、删除源失败、移动源失败、清理解压失败残留等）。
   - 效果：失败原因即时出现在界面的失败记录里，无需打开日志文件。
